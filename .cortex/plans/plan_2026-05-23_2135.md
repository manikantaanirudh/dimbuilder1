## Implementation Plan: Approval Workflow Engine (Feature 2)

### Context

**Key findings from exploration:**
- The project uses a `createRepositories(db)` function that returns a large object with method groups (`projects`, `changeSets`, `users`, etc.) — type is `ReturnType<typeof createRepositories>`
- Routes follow the pattern: `export function createXxxRouter(repos: Repositories, config: AppConfig): Router` registered in `app.ts`
- Tests use in-memory SQLite (`createDatabase(":memory:")`) with `app.listen(0)` and `fetch()` calls
- Schema lives in a single `schemaSql` template literal exported from `src/server/db/schema.ts`
- Config types are in `src/shared/appConfigTypes.ts`, defaults in `src/shared/appConfigDefaults.ts`
- Zod is used for request validation in route files (see `users.ts`, `auth.ts` patterns)
- `nanoid()` for all IDs, `new Date().toISOString()` for timestamps
- Client API calls use `apiGet`, `apiPost`, `apiPatch`, `apiPatchJson` helpers in `src/client/api/client.ts`
- DimensionWorkspace already has a "Change Sets" tab — the workflow UI can either be added as a new tab or integrated alongside
- The `req.user` object has `id`, `email`, `role` fields after auth middleware
- `ClientAppConfig = Omit<AppConfig, "paths" | "server" | "auth">` — workflow config will be exposed to client

### Implementation Steps

#### Step 1: Create shared types (`src/shared/workflowTypes.ts`)
Create the `WorkflowStatus`, `WorkflowStepAction`, `WorkflowStepDefinition`, `WorkflowDefinition`, `WorkflowInstance`, `WorkflowStepActionRecord`, `WorkflowNotification`, `WorkflowInstanceDetail`, `SubmitWorkflowRequest`, `WorkflowActionRequest` types as specified.

#### Step 2: Extend database schema (`src/server/db/schema.ts`)
Append the 4 new tables and 4 new indexes to the `schemaSql` template literal string.

#### Step 3: Add workflow config to appConfigTypes + defaults + YAML
- Add `WorkflowConfig` interface to `src/shared/appConfigTypes.ts`
- Add `workflows?: WorkflowConfig` to `AppConfig`
- Add defaults to `src/shared/appConfigDefaults.ts`
- Add `workflows:` block to `config/dimbuilder.yaml`

#### Step 4: Add repository methods (`src/server/db/repositories.ts`)
Add a `workflows` namespace to the repos object:
- `definitions.create()`, `definitions.list()`, `definitions.get()`, `definitions.update()`
- `instances.create()`, `instances.get()`, `instances.getDetail()`, `instances.listByProject()`, `instances.listByStatus()`, `instances.updateStatus()`, `instances.advanceStep()`
- `stepActions.record()`, `stepActions.listByInstance()`
- `notifications.create()`, `notifications.listByRecipient()`, `notifications.markRead()`
- `getEligibleReviewersForStep()` — query users with the required role

#### Step 5: Create workflow engine (`src/server/workflow/workflowEngine.ts`)
Core state machine with functions:
- `submitWorkflow(repos, config, changeSetId, definitionId?, submittedBy)` — validates preconditions, creates instance, notifies reviewers
- `approveStep(repos, instanceId, actorId, comment?)` — validate role/self-approval, record action, check minApprovals, advance or complete
- `rejectWorkflow(repos, instanceId, actorId, comment?)` — record reject, set status, update change set
- `cancelWorkflow(repos, instanceId, actorId)` — only submitter/admin can cancel

#### Step 6: Create workflow routes (`src/server/routes/workflows.ts`)
Following users.ts patterns with Zod validation:
- `GET /api/workflows/definitions` — list active definitions
- `POST /api/workflows/definitions` — admin only, create definition
- `PATCH /api/workflows/definitions/:id` — admin only, update
- `POST /api/workflows/submit` — submit change set into workflow
- `GET /api/workflows/instances` — list with ?projectId & ?status filters
- `GET /api/workflows/instances/:id` — detail view
- `POST /api/workflows/instances/:id/approve` — approve
- `POST /api/workflows/instances/:id/reject` — reject
- `POST /api/workflows/instances/:id/cancel` — cancel
- `GET /api/workflows/my-pending` — user's actionable items
- `GET /api/notifications` — user notifications
- `PATCH /api/notifications/:id/read` — mark read

#### Step 7: Wire routes into `app.ts`
Add `import { createWorkflowRouter } from "./routes/workflows"` and `app.use("/api/workflows", createWorkflowRouter(repos, config))` plus notification routes.

#### Step 8: Seed default workflow definition (`src/server/db/database.ts`)
Add `seedDefaultWorkflow(db)` in `createDatabase()` that inserts "Standard Review" definition if not exists.

#### Step 9: Create client components
- `src/client/components/WorkflowPanel.tsx` — shows pending workflows, history, submit/approve/reject actions
- Add workflow API functions to `src/client/api/client.ts`
- Add "Workflows" tab option to `DimensionWorkspace.tsx` (alongside existing "Change Sets" tab)

#### Step 10: Write integration tests (`src/test/workflow.test.ts`)
8 test cases matching the spec:
1. Create workflow definition
2. Submit change set into workflow
3. Approve → workflow advances and completes
4. Reject → workflow rejected, change set status updated
5. Self-approval prevention
6. Role requirement enforcement
7. Cancel workflow
8. List pending workflows for a user

#### Step 11: Run full test suite
Execute `npx vitest run` to verify no regressions.
