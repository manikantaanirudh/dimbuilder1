## Implementation Plan

### Context

**Key findings from exploration:**
- The issue-filter bug is a pagination problem: filtering is client-side but the grid is server-paginated, so only the current page's records get filtered
- Validation engine already supports configurable severities — adding per-project overrides via DB is natural
- Config is loaded once at startup and passed by reference to all routers — supporting runtime updates requires a mutable config holder
- CSS uses CSS custom properties in `:root` making theme changes straightforward
- No per-project settings table exists yet — needs to be created

---

### Step 1: Fix Issue Filter Bug (Server-Side Filtering)

**Problem:** `filteredRecords` only applies to the current page of records (600 rows). Issues referencing records on other pages are invisible.

**Fix:** Add a server-side `?ids=` query parameter to the members/relationships endpoints.

- **`src/server/db/repositories.ts`** — Add `listByIds(dimensionId, ids)` method that returns records matching specific IDs
- **`src/server/routes/projects.ts`** — Modify GET members/relationships endpoints to accept `?ids=id1,id2,...` param. When present, return those specific records (no pagination) instead of the regular paginated response
- **`src/client/api/client.ts`** — Add optional `ids` parameter to `fetchMembers`/`fetchRelationships`
- **`src/client/components/EditableGrid.tsx`** — When `issueFilteredIds` is non-null, fetch using the IDs-based endpoint instead of regular pagination. Disable pagination controls while filter is active.

### Step 2: Per-Project Validation Rule Toggles

**Database:**
- **`src/server/db/schema.ts`** — Add new table `project_validation_overrides` with columns: `id`, `project_id`, `rule_code TEXT`, `severity TEXT` (error/warning/info/off), `updated_at`
- **`src/server/db/repositories.ts`** — Add `validationOverrides` repository (list, upsert, delete by project)

**Server:**
- **`src/server/routes/projects.ts`** — Add GET/PUT endpoints: `GET /:projectId/validation-config` and `PUT /:projectId/validation-config`
- **`src/server/routes/validation.ts`** — Before running validation, load project overrides from DB and merge them into the severities config (any rule set to "off" gets skipped)
- **`src/shared/validationEngine.ts`** — Support `"off"` as a valid severity that causes `addIssue` to skip. Add a simple check: `if (severity === "off") return;`
- **`src/shared/appConfigTypes.ts`** — Extend `Severity` type to include `"off"`

**Client:**
- **`src/client/components/AdminPanel.tsx`** — Transform from read-only table to editable: add toggle switch per rule (on/off) and severity dropdown. Add "Save" button that calls the new API. Load per-project overrides on mount.

### Step 4: Frontend Config Editor (Live Apply)

**Architecture:** Store config as a mutable reference. Add API endpoint to read/write the full config. On save, persist to YAML and update the in-memory config object.

- **`src/server/app.ts`** — Wrap config in `{ current: AppConfig }` holder passed to all routers. Routers read `configHolder.current` instead of a direct reference.
- **`src/server/routes/config.ts`** — Add `PUT /api/config` endpoint that: validates the submitted config, deep-merges onto defaults, writes to `dimbuilder.yaml`, and updates `configHolder.current`
- **`src/client/components/ConfigEditor.tsx`** — New component: YAML/form editor. Load config via existing `GET /api/config`, provide a form or YAML text editor, save via new `PUT /api/config`
- **`src/client/components/AppShell.tsx`** — Add "Config" tab to Admin or as separate nav item. After save, reload the client config via `useAppConfig` hook refresh.
