## Implementation Plan: Feature 6 — Multi-Environment Management

### Context

**Key findings from exploration:**
- SQLite database with schema defined as a multi-statement string in `src/server/db/schema.ts`
- Repositories are all in a single monolithic `createRepositories()` function in `src/server/db/repositories.ts` (2504 lines), using `nanoid` for IDs and a `now()` helper
- Routes are Express routers with Zod validation, mounted in `src/server/app.ts`
- Client API uses `apiGet`, `apiPost`, `apiPatch`, `apiPatchJson`, `apiDelete` from `src/client/api/client.ts`
- Tests use vitest, spin up in-memory DB + HTTP server per `describe`, register admin/viewer users
- React components are functional, using standard props typing (no hooks-heavy patterns)
- Existing `environments` repo has `list()`, `getById()`, `getSafe()`, `create()`, `update()`, `delete()`

### Implementation Steps

**Step 1: `src/shared/multiEnvTypes.ts`** — Type definitions
- `SyncStatus` = "in_sync" | "local_ahead" | "remote_ahead" | "diverged" | "unknown"
- `PromotionStage` = { environmentId, order, name, requiresApproval }
- `PromotionPipeline` = { id, name, stages, isActive, createdBy, createdAt, updatedAt }
- `EnvironmentSyncStatus` = { id, environmentId, projectId, dimensionType, lastDeployedAt, localVersionHash, syncStatus, checkedAt }
- `EnvironmentOverride` = { id, environmentId, projectId, dimensionType, memberKey, propertyName, overrideValue, reason, createdBy, createdAt, updatedAt }
- `PromotionRecord` = { id, pipelineId, projectId, fromEnvironmentId, toEnvironmentId, deploymentId, status, promotedBy, promotedAt }

**Step 2: `src/server/db/schema.ts`** — Add 4 tables at end of schema string
- `promotion_pipelines` (id, name, stages_json, is_active, created_by, created_at, updated_at)
- `environment_sync_status` (id, environment_id, project_id, dimension_type, last_deployed_at, local_version_hash, sync_status, checked_at, UNIQUE(environment_id, project_id, dimension_type))
- `environment_overrides` (id, environment_id, project_id, dimension_type, member_key, property_name, override_value, reason, created_by, created_at, updated_at)
- `promotion_history` (id, pipeline_id, project_id, from_environment_id, to_environment_id, deployment_id, status, promoted_by, promoted_at)
- Indexes on each table

**Step 3: `src/server/db/repositories.ts`** — Add 4 repository sections
- `promotionPipelines`: list, getById, create, update, delete
- `environmentSyncStatus`: list (by env/project), upsert, getByEnvProjectDim
- `environmentOverrides`: list (by env/project), create, update, delete
- `promotionHistory`: list (by pipeline/project), create
- Add mappers for each row type

**Step 4: `src/server/environments/syncStatus.ts`** — Service module
- `computeLocalHash(repos, projectId, dimensionType)` — SHA-256 of members+relationships for a given dimension type within a project
- `refreshSyncStatus(repos, projectId, environmentId?)` — recompute hash for each dim type, compare with last deployed hash, upsert sync status
- `getSyncStatusSummary(repos, projectId)` — aggregate sync statuses grouped by environment

**Step 5: `src/server/routes/environments.ts`** — Extend existing router
- `GET /pipelines` — list pipelines
- `POST /pipelines` — create pipeline (Zod validation)
- `POST /pipelines/:id/promote` — execute promotion (deploy from source env to target env)
- `GET /projects/:id/sync-status` — get sync status summary for a project (mounted under environments path)
- `POST /sync-status/refresh` — trigger sync status refresh
- `GET /env-overrides` — list overrides (query params: environmentId, projectId)
- `POST /env-overrides` — create override
- `PATCH /env-overrides/:id` — update override
- `DELETE /env-overrides/:id` — delete override

**Step 6: `src/client/components/MultiEnvDashboard.tsx`** — React component
- Props: pipelines, syncStatuses, overrides, environments, onPromote, onRefreshSync, onCreateOverride, onDeleteOverride
- Summary cards showing environment count, sync status breakdown
- Pipeline list with promote actions
- Override table with CRUD
- Follows pattern from `ValidationDashboard.tsx`

**Step 7: `src/client/api/client.ts`** — Add API functions
- `fetchPipelines`, `createPipeline`, `promotePipeline`
- `fetchSyncStatus`, `refreshSyncStatus`
- `fetchEnvOverrides`, `createEnvOverride`, `updateEnvOverride`, `deleteEnvOverride`

**Step 8: `src/test/multiEnv.test.ts`** — Test file
- Standard vitest pattern (in-memory DB, HTTP server, admin/viewer tokens)
- Test groups: pipeline CRUD, sync status computation/refresh, overrides CRUD, promotion flow
- ~15-20 test cases covering happy paths, validation failures, 404s
